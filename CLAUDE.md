# Altegio.Pro MCP Server - Project Context

## Overview
MCP (Model Context Protocol) server for Altegio.Pro business management API.
- **Target users**: Local service business owners, administrators and team members
- **Focus**: B2B authenticated operations only (no public B2C booking)
- **Tech**: TypeScript, @modelcontextprotocol/sdk, Express for HTTP mode
- **Package**: `@altegio/mcp-server-pro` (not published to npm)

### Architecture

**Transports:**
- **stdio** (default) → `dist/index.js` → Claude Desktop integration
- **HTTP** → `dist/http-server.js` → Production on VM (port 3000). Customers: `https://mcp.alteg.io/pro` (+ `/pro/<facet>`, `/pro/readonly`; Altegio sign-in; `/public/pro/mcp…` is a kept alias). Staff: `https://mcp.altegio.dev/pro/mcp…` (Google sign-in; the old `mcp.alteg.io/pro/mcp…` form stops answering at the 2026-09-28 cut). Never rewrite a `/public/pro/mcp` address to `https://mcp.alteg.io/pro/mcp` — that is the staff lane
  - `/health` - health check
  - `/mcp` - MCP Streamable HTTP (POST for messages, GET for SSE stream, DELETE for session termination)
  - `/mcp/<facet>` - the same protocol on a static filtered tool list; facets: `ops`, `catalog`, `finance`, `marketing`, `analytics`, `onboarding` (ADR-001 D3). stdio uses the unfiltered `all` view and always exposes everything.
  - `/mcp/readonly` - the read-only view. **Not a seventh facet**: facets ration context, this rations what an agent may do. Membership is computed from `readOnlyHint: true`, never a hand list; a write tool is refused on call, not merely hidden. See the change entry below.
  - **Withheld from HTTP by default:** `altegio_login`/`altegio_logout` (password prompt under an OAuth endpoint — set `ALTEGIO_EXPOSE_PASSWORD_LOGIN=true` only for the closed staff deployment) and, from the default `/mcp` view only, `remove_location_user` (access management; still on `/mcp/catalog`). Both stay on stdio.

**Resources & prompts:**
- Resources: `altegio://docs/product-logic`, `altegio://docs/glossary`, `altegio://docs/onboarding-guide`
- Prompt: `onboarding_walkthrough`
- A pack plugs in by exporting one module and adding an import line to `src/resources/index.ts` or `src/prompts/index.ts`

**Authentication:**
- Partner token: `ALTEGIO_API_TOKEN` (required, from https://developer.alteg.io)
- User token: obtained via `altegio_login`, saved to `~/.altegio-mcp/credentials.json`
- API headers: `Authorization: Bearer {partner_token}`, `User-Token: {user_token}` (To access internal information)

**Key Files:**
- `src/index.ts` - stdio entry point
- `src/http-server.ts` - HTTP server entry point
- `src/providers/altegio-client.ts` - API client (auth, retry, rate-limit)
- `src/tools/handlers.ts` - tool implementations
- `src/tools/registry.ts` - MCP tool definitions
- `src/types/altegio.types.ts` - TypeScript types
- `src/utils/` - logging, errors, config, credential manager

**Scope vocabulary fix — the gate was refusing everything (2026-09-17)**
- **The premise of the entry below was false.** It assumed no deployment sent `x-mcp-auth-scope`. `mcp-proxy/routes.json` declares `scopes: ["mcp:pro:read","mcp:pro:write"]` on `/pro` **and** `/public/pro`, both pointing at this backend (10.132.0.3:3000); `/pro` carries `forward_identity: true`, so `lib/as.js` (scope filtered to the route's list) → `lib/rs.js` (`req.auth.scope`) → `lib/identity-headers.js` forwarded `x-mcp-auth-scope: "mcp:pro:read mcp:pro:write"` on every call. Those names parse as valid scope tokens, so `granted` was non-empty; none matched a v3 `domain:action` requirement, so **every gated tool was refused on the closed endpoint.** Reproduced before fixing.
- **Two vocabularies, one rule, one file.** `src/tools/scopes.ts` now states where each vocabulary comes from, which is temporary and what happens to an unknown one. v3 `domain:action` = the requirement language (no token carries it yet). Platform `mcp:pro:*` = what actually arrives, deleted when v3 lands.
- **`mcp:pro:write` satisfies EVERY requirement, action-scopes included** (`appointments:create`, `team_members:manage_access`, `analytics:write`); `mcp:pro:read` satisfies only `:read`. Decided explicitly, not silently: the v3 split is meaningful because a v3 token can express it, the platform pair cannot — two grades for the whole service, no third grant obtainable. Withholding the action-scopes would make `create_appointment` and `onboarding_create_test_appointments` permanently unreachable rather than strictly guarded, i.e. the same outage, narrower. `manage_access` is admitted with open eyes: `remove_location_user` is already withheld from `/mcp`, so the narrowing that matters for it is the address.
- **An unrecognised vocabulary restricts nothing** — restores #51's actual intent. `grantIsRecognised` accepts the platform pair and any v3 name whose domain appears in `KNOWN_SCOPES`; a grant with nothing recognised (another service's scopes, a rename upstream, `openid email`) passes through and logs once per distinct grant. Failing closed on an unknown name turns any upstream rename into a total outage. Accepted trade, documented: a token holding *only* `mcp:bi-data:read` or `visits:read` would be unrestricted — the proxy's RS rejects those before they reach us (audience + scope intersection).
- **`/mcp/readonly` is a real boundary now, not only a guardrail** — the proxy can already issue `mcp:pro:read` alone, and such a session is refused every write on **every** address, `/mcp` included, before the handler runs. Guardrail only when the grant is full or absent. Corrected in `README.md` and in a correction paragraph under the ADR-001 D3 addendum.

**Token-scope check on execution (2026-09-17)**
- **The `x-mcp-auth-scope` header is finally read.** The OAuth proxy has been forwarding the caller's granted scopes since the platform shipped; `src/request-context.ts` parsed it into `RequestIdentity.scope` and nothing used it. Every tool now declares what its execution requires and the `tools/call` handler enforces it.
- **Why:** the v3 authorization RFC settled that the boundary is the token's scope — the spec forbids treating annotations as a security decision, and a separate address only picks a rights profile. Until this, the server had no boundary at all, and nothing to restrict with when v3 starts issuing narrowed tokens.
- **Placeholder names, live enforcement.** The v3 scope names are PLACEHOLDERS: the shape follows the ratified v3 convention (`domain:action`) and most names are verbatim from `../biz.erp/docs/research/api-standardization/v3-plan/scope-catalog.md`, which is explicitly not final and owned by the API team. `analytics:*` and `api:read` had to be invented — no v3 domain covers reports, and the universal executor reaches every documented GET under one tool name. The gate is nonetheless live, because the grants that arrive are the platform's, not v3's — see the 2026-09-17 vocabulary fix below.
- **One map file:** `src/tools/scopes.ts` holds the vocabulary, the tool→scope map, the satisfaction rule and the refusal text. No tool definition names a scope — `defineTool` fills `ToolDefinition.requiredScopes` from the map by tool name, so approving a different vocabulary is one edit, not seventy. A coverage test fails the build when a tool has no entry.
- **Execution only (ADR-001 D7):** `tools/list` is never filtered by the caller's scopes; one path serves one tool list to every connection. A tool a caller cannot run is still listed and explains itself when called. Pinned by an e2e test over three sessions with different grants.
- **No-op for an unscoped caller:** stdio and `/public/pro` (no `forward_identity` on that route) declare no scopes and pass straight through. A malformed header counts as "not declared" rather than "empty grant", so a proxy bug cannot refuse every call. Scope tokens are validated against the RFC 6749 grammar on the way in, so echoing them into a refusal cannot smuggle markup into model context. **This bullet originally claimed every deployment was unscoped — it was wrong; see the fix below.**
- **Implication (within the v3 vocabulary):** only `X:write ⊇ X:read` on the same domain (v3 A8/F-13). `create`, `manage_access`, `capture`, `refund` are never implied; `chain_*` never satisfies a location scope. `clients:read_contact` is a field gate V1 cannot express and is deliberately not faked. The platform vocabulary has its own, coarser rule — below.
- **Refusal is in band:** an `isError` result, same channel as the confirmation gate — never an HTTP 403 (drops the session) and never upstream API text. Hosts do not re-authorise on a mid-session denial (Claude Code closed that as "not planned", April 2026), so the message says not to retry and tells the model to route a named missing permission to a person.
- **Order:** the scope check runs BEFORE the confirmation gate, so a call the token cannot authorise never prompts a human and never makes the API read that resolves the prompt's target.
- **Files:** `src/tools/scopes.ts` (new), `src/tools/factory.ts`, `src/tools/registry.ts`, `src/request-context.ts` (`parseScopes`, `getRequestScopes`), `README.md`. Tests: `src/tools/__tests__/scopes.test.ts`, `src/__tests__/scope-enforcement-e2e.test.ts` (real HTTP sessions through `createApp()`).

**Read-only address `/mcp/readonly` (2026-09-17)**
- **A separate URL, because that is the only restriction hosts and the protocol both respect.** Outcome of the v3 authorization RFC: consent stays all-or-nothing (no per-scope checkboxes), and an agent is narrowed by pointing it at a different address — how GitHub, Linear, Sentry, Stripe, Notion, Atlassian and Slack do it. A separate URL is a separate OAuth resource, so a different `tools/list` there is legal. `X-MCP-Readonly` was rejected: a caller-set header enforces nothing, Claude Desktop does not send one, and it would vary `tools/list` on one resource (ADR-001 D7).
- **Not a seventh facet.** Facets (`ops`, `catalog`, …) answer "how many tools fit in this host's context"; readonly answers "what may this agent do". `READONLY_VIEW` is a view of the same kind as `DEFAULT_FACET` / `ALL_TOOLS_FACET`, outside `FACET_NAMES`, and never offered as a destination by `facetsProviding`.
- **Membership is computed, never listed.** `buildFacetIndex` now takes `FacetTool[]` (`{name, readOnly}`) instead of names; `readOnly` is `annotations.readOnlyHint === true` and nothing else, fail-closed. 30 of the 66 served tools today. A future pack joins automatically; `facets.test.ts` fails if anything without the annotation reaches the view. Base tools are **not** force-admitted here (unlike a facet), and the default view's prefix exclusions do not apply — so the whole analytics pack is served, which `/mcp` holds back.
- **Refused, not just hidden.** Same mechanism as password login (PR #45): the facet gate in `src/tools/registry.ts` rejects the call. The readonly branch returns an actionable message naming the **full** address of the complete surface, because hosts do not re-authorize on a refusal (Claude Code closed that request as "not planned", April 2026) — no step-up to hint at. It stays an in-band JSON-RPC error; a tool refusal never becomes an HTTP status.
- **Its own `initialize` instructions** (prefixed to the product text, so an `MCP_SERVER_INSTRUCTIONS` override still gets them): the surface only reads, nothing unlocks it, and suggest the full address only if the user actually wants an agent that can change their data.
- **`WWW-Authenticate` (RFC 9728): nothing to do here.** This server emits only 400/404/500; authentication is entirely the mcp-proxy's, which forwards an already-verified identity as `x-mcp-auth-*`. The header belongs on whoever returns the 401.
- **Honest scope:** while v3 issues one full token, this is a **guardrail, not a security boundary** — the same token can write, and a person can drive the API around MCP. Its value today is letting the consent screen stay all-or-nothing. Documented for developers/enterprise only; not in onboarding or the marketplace.
- **New env `MCP_PUBLIC_BASE_URL`** (default `https://mcp.alteg.io/public/pro`), used only to name addresses in that refusal and those instructions. **Superseded 2026-09-23 (#63):** it is now the address of the complete surface, default `https://mcp.alteg.io/pro` — see the entry above.
- **Files:** `src/tools/facets.ts`, `src/tools/registry.ts`, `src/config/schema.ts`, `src/server.ts`, `src/http-server.ts` (route registered before the `/mcp/:facet` catch-all), `README.md`. Tests: `src/tools/__tests__/facets.test.ts`, `src/__tests__/{mcp-surface,http-server,config}.test.ts`.

**Public HTTP surface hardening (2026-09-17)**
- **Password login off the HTTP surface:** `altegio_login` / `altegio_logout` left `FACET_BASE_TOOLS` for a new `PASSWORD_LOGIN_TOOLS` list, admitted to the default view and the named facets only when `ALTEGIO_EXPOSE_PASSWORD_LOGIN=true`. **Why:** the login description tells the model to ask the user for an email and a password; on the public endpoint, which is under OAuth and never needs them, that is a standing prompt-injection target. **Human confirmation before destructive operations (2026-09-17)**
- **11 destructive tools now ask a person first** — `delete_staff`, `delete_service`, `delete_service_category`, `delete_schedule`, `delete_appointment`, `delete_booking_form`, `clients_delete`, `unlink_service_team_member`, `remove_location_user`, `onboarding_rollback_phase` and the withheld `analytics_delete_assistant_report`.
- **Why:** `destructiveHint` is a hint the spec forbids clients from treating as a security boundary, and it protects nothing on an autonomous agent. Elicitation is the protocol's own answer: the server asks, regardless of host configuration.
- **Two paths, chosen from client capabilities at `initialize`:** with `elicitation` → an `elicitation/create` form naming the resolved object ("team member Ivan Petrov, Stylist, id 123") and the consequence; runs only on an explicit accept, and a decline/cancel/failed prompt stops the call with no token issued. Without it → the first call performs nothing and returns the consequence plus a one-time `confirmation_token`; the identical call repeated with that token proceeds. Without the fallback the call would hang on an older host.
- **Token:** HMAC over tool name + exact arguments, keyed per process, 10-minute TTL, refused (not ignored) when it does not verify. Bound to the arguments, so a confirmation for client 5 never authorises deleting client 7. No server-side state, so `tools/list` stays static (ADR-001 D7) — `confirmation_token` is an always-present optional argument, never negotiated per client.
- **Every non-approval outcome is an `isError` result** (confirmation required, declined, prompt undeliverable, invalid token) — same channel as `ExecutorRefusalError`, so a model cannot read "cancelled" as "deleted", and a gate result stays legal for a tool that declares an `outputSchema` (a client rejects a non-error result with no `structuredContent`).
- **Declarative:** `confirm` on `ToolDefinition` (`src/tools/factory.ts`) adds both the schema argument and the gate registration; the hand-written onboarding spec declares it through `onboardingConfirmations`. Enforcement is in exactly one place — the `tools/call` handler in `src/tools/registry.ts`, the only code path holding both the `Server` and the request id `relatedRequestId` needs.
- **Files:** `src/tools/confirmation.ts` (new), `src/tools/factory.ts`, `src/tools/registry.ts`, `src/tools/onboarding-registry.ts`, the 8 definition modules with a destructive tool, `README.md`. Tests: `src/tools/__tests__/confirmation.test.ts` (token + gate units), `src/__tests__/destructive-confirmation-e2e.test.ts` (both host kinds over a real `Client` ↔ `Server` pair), `src/tools/__tests__/destructive-coverage.test.ts` (every `destructiveHint: true` tool has a gate).

**Two-fork, per-request authentication (2026-09-09)**
- **The Pro MCP now serves two B2B use cases, chosen per request by the presence of `X-Altegio-*` headers:**
  - **UC1 — human via a generic agent (no `X-Altegio-*` headers):** unchanged. The server signs upstream calls with its OWN partner token (`ALTEGIO_API_TOKEN`); the caller reaches Altegio through `altegio_login` (email + password → user token, stored per identity).
  - **UC2 — application agent (`X-Altegio-Partner-Token` present):** the caller sends its own partner token + `X-Altegio-User-Token` per request. The upstream credential is `Authorization: Bearer <per-request partner>, User <per-request user>` — the server partner token is never used for these calls.
- **Fork selector:** `X-Altegio-Partner-Token` present → UC2; absent → UC1 (`getRequestPartnerToken() ?? this.partnerToken` in `apiRequest`).
- **Declared company-ID set (`X-Altegio-Company-Id`):** optional scope, supporting MULTIPLE IDs (repeated header and/or comma-separated). Trusted exactly as declared — the MCP does not validate/compute/resolve which companies belong to the caller. `list_locations` is filtered to the set; any request targeting a company outside the set is refused with a 403 (only that ID). Enforced centrally in `AltegioClient.apiRequest` (the one choke point every CRUD tool, the analytics/clients ports, and the executor funnel through) by extracting the location ID as the first numeric path segment, plus an early gate in `resolveLocationTimezone`.
- **Supersedes PR #34 (`feat/company-id-scope`):** generalizes its single-company pin (`companyId?: number`, `assertCompanyAllowed`, single `list_locations` filter) to a set (`companyIds?: ReadonlySet<number>`).
- **Files:** `src/request-context.ts` (`parsePartnerToken`, `parseCompanyIds`, `getRequestPartnerToken`, `getRequestCompanyIds`, `isCompanyAllowed`, `assertCompanyAllowed`), `src/providers/altegio-client.ts` (per-request partner + central scope guard + `list_locations` filter), `src/http-server.ts` (parse + thread both headers on every route), `src/capabilities/analytics/location-timezone.ts` (early scope gate). ### Common Patterns

**Authentication check in handlers:**
```typescript
if (!this.client.isAuthenticated()) {
  throw new Error('Authentication required');
}
```

**Authentication check in client methods:**
```typescript
async getStaff(companyId: number) {
  if (!this.userToken) {
    throw new Error('Not authenticated');
  }
  // ... API call
}
```

**Secrets Management:**
- Local: `.env` file (gitignored)
- Never commit tokens to git

**Test isolation:**
- Tests default to `~/.altegio-mcp/` credentials
- Pass `testDir` parameter to use isolated test directory:
  ```typescript
  new AltegioClient(config, testDir)
  ```
