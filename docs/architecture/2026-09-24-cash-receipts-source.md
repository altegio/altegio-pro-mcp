# Customer cash receipts: source contract (2026-09-24)

`analytics_get_client_cash_receipts` answers the monthly cash-basis part of Timur's reports. It is a read-only, location-scoped finance aggregate. It does not use the `manual_cost` service value in `analytics_get_service_mix_trend`, and it does not produce payer cohorts.

## Backend trace

- Route: authenticated ERP `GET /finances_reports/annual_report/{location_id}/` (`PageFinancesReportsController::action_annual_report`). It requires `finances_year_report_access`; when the report-constructor feature hides system reports, the route redirects and the transport refuses it. The request-scoped user token is injected by `requestLegacyWebReport`, with no browser cookie or persisted session.
- Before that read, documented V1 `GET /user/permissions/{location_id}` verifies the effective annual-report right and account boundary for the same request identity. The backend finance filter treats an empty allowed-account list as no filter; for a user with `finances_accounts_limited_access=true`, this tool refuses an empty or malformed `finances_accounts_ids` list so that the report cannot inadvertently widen to all accounts. Missing permission metadata also fails closed.
- `getAnnualData` selects active (`st=YES`) finance transactions in authorized location accounts. It rounds the requested start down to the first day of its month and end up to the last day of its month. The tool therefore accepts only complete local calendar months, at most 12. The controller uses `dateAtTimezoneFilter` for the location; `CTableReportPeriod::fillData` assigns each transaction to its local month.
- `CTableReportPeriod` sums each signed transaction amount once by finance income category, using the stable `type` ID in a transaction drill-down link. It exposes a monthly income row and a period total. Account transfers without an income category do not enter the income rows. Canceled transactions are excluded by the source filter. A negative active transaction reduces the month/category net. The source does **not** split positive receipts from refunds or identify the corresponding original transaction.
- The category list includes standard categories and only active, location-linked custom categories (`ExpensesStorage::getBySalonIdsWithStandard`). A posted transaction in a subsequently disabled custom category can be omitted from this report. Reconciliation proves internal consistency of the rendered source, not completeness against every historical ledger row.
- Standard transaction type IDs come from `CTransactions`: service payment 5, product sale 7, miscellaneous income 8, client-account top-up 10, membership sale 6, certificate sale 12, and no-show penalty 13. The first four match the supplied PDF's core cash streams; memberships, certificates and penalties remain explicit rather than silently folded into miscellaneous income. All other income IDs are summed as unclassified posted income. An unclassified category may or may not represent customer cash, so `classified_client_cash_net` excludes it; `posted_income_net` includes it.
- The parser checks one report table, expected month-column count, every row width, local month drill-down dates, unique positive category IDs, each row total, every monthly category sum against the income aggregate, and the period income total. A changed page or mismatch fails the whole call. The transport caps the HTML at 2 MiB. This is a complete source aggregate for the user's authorized accounts, not a transactional snapshot. The backend builds it from an unbounded transaction list; a busy clinic can time out or exceed the response cap, in which case the tool returns no partial total.

## Cash and privacy boundary

Client-account top-ups are a finance cash receipt; later spending of the deposit balance is a loyalty/deposit operation, not a second cash receipt in this report. `DepositBalanceChangeHandler` and `DepositsOperationsService` link top-ups to transaction type 10. `CTransactions` type 5 and type 7 are posted money transactions; loyalty deductions and historical service `manual_cost` are separate measures. The source's account permissions may hide accounts, so these totals are **authorized-account source totals**, not guaranteed whole-business ledger totals.

The report returns amounts and month keys only. It carries no names, phone numbers, email addresses, comments, or payment IDs. It reports signed **net** cash by stream. Gross receipts, refund totals, account-by-account reconciliation, a snapshot identifier, and custom income's customer meaning are unavailable.
The currency is emitted only when location metadata supplies an ISO 4217 code; otherwise it is `null`, never guessed from a symbol.

An authorized read-only smoke on demo location 4564 for August 2026 returned a nonzero, internally reconciled month. Its income total matched the existing P&L adapter on the same period. No client data or raw response was retained.

## Payer cohort investigation and decision

The finance web list `GET /finances/transactions_search/{location_id}/` is paged with an exact count and stable transaction IDs (`data-locator`), but `templates/finances/transactions/search.php` renders payer **names**, not client IDs. `GET /finance_transactions/{location_id}/{transaction_id}` returns a client ID and signed amount. The list silently clamps the start date to `finances_last_days_count` in `FinanceTransactionsService::getDate`, without returning an effective period. The earlier conclusion that this made all payer cohorts unavailable was too strong: it ruled out bounded, checked detail reads without testing them.

The existing `analytics_get_client_sales` source is not a substitute: `ReportProfit::getData(GROUP_BY_CLIENT)` composes goods transactions and attended service `cost` by visit period, not signed finance receipts or account top-ups. A client card's lifetime paid amount likewise has no selected-period cash basis. Names are never matched to IDs.

`analytics_get_client_payer_cohorts` now uses the narrow finance route only to enumerate IDs and **local display dates** for the four cash streams in Timur's PDF (category IDs 5, 7, 8 and 10). It reads each selected ID from documented V1 finance detail for client ID, category, account and signed amount. The detail date is not used to assign the local month (see below). The tool checks the user's finance-report, transaction-list and finance rights; it requires `finances_last_days_count=-1` and refuses an empty account allowlist for account-limited users. Every selected transaction is checked against that list. Each category and month must reconcile exactly to the annual finance report. After detail reads the tool enumerates the list again and requires identical IDs and local dates. A missing page, changed list, refused detail or failed reconciliation aborts the whole call.

The call accepts at most 12 complete months and 4,000 selected transactions. It uses 16 bounded concurrent V1 reads. Identified clients with **positive period net cash** enter the payer ranking; clients with zero/negative net and payments without a client ID are separate. Rankings sort by net cash descending and client ID ascending; the first and next `floor(N/10)` clients form the top and next decile, and the rest form the final cohort. One cohort's stable client IDs are paged without contacts. The monthly finance report still includes memberships, gift cards, penalties and unclassified income, but those are outside this four-stream payer base.

The live demo location had 292 total August 2026 finance transactions, of which 289 were selected service payments. A 12-month September 2025–August 2026 check joined and reconciled 913 selected transactions in about 27 seconds, finding 115 positive-net payers and cash without a client ID. Only aggregate diagnostics were retained. The source has no transactional snapshot: the second list pass plus monthly reconciliation detects many concurrent edits but cannot prove an immutable point-in-time ledger. Other clinics can exceed the cap or gateway time budget; the tool refuses rather than returning partial cohorts. A server-side V3 aggregate remains the scalable replacement.

### Local month source (verified 2026-09-24)

- **The list date does not depend on locale.** `templates/finances/transactions/search.php` renders the date cell as `date('d.m.y', $ts)`, a `<br />`, then `date('H:i:s', $ts)` with `$ts = tsAtTimezone($transaction->getDate(), $salonId)`. PHP `date()` patterns are hard-coded and ASCII: the user's interface language changes only the column headers, and the location's EU/US date-format setting (`DatetimeFormatFactory`, `d.m.Y` or `n/d/Y`) decides only how `action_transactions_search` parses `start_date`/`end_date`. ISO input is accepted there through the `date_create` fallback in `DateUtils::createFromString`.
- **It is the report's own month assignment.** `tsAtTimezone` adds the same server-to-location shift as `dateAtTimezone`, which `CTableReportPeriod::fillData` applies before it buckets a transaction into a month of the annual report; the list filter subtracts it through `dateAtTimezoneFilter`, as the report does. Both use the location's *current* UTC offset rather than the offset at the transaction instant, so near a DST change a midnight transaction can move to the neighbouring day between seasons — the list and the report move together, the reconciliation still holds, and the second list pass detects a change during one call.
- **The V1 detail date is not location-local.** `TransactionTransformer` returns `CTransactions::getDate()`, the stored server time (`Asia/Dubai`, written through `setDateInSalon` → `convertSalonTimeToServerTime`), without an offset; the public spec example shows an offset the backend never sends. Deriving the month from it would re-implement the legacy shift above, so it is not used.
- **Parser contract.** `src/api/v1/finance-transactions-parser.ts` accepts exactly `DD.MM.YY HH:MM:SS`, resolves the two-digit year within the at most two calendar years of the request, and refuses every other shape (a four-digit year, the US location format with 12-hour time, ISO), impossible dates, rows outside the period, cancelled or unidentified rows and missing or duplicated rows. It skips the unlabelled page-total row, and reads no payer name, comment or amount. A golden fixture shaped like the template pins it.

The disabled Analytics Constructor report-data operations remain disabled. A future V3 finance read model can replace this temporary HTML adapter without changing the MCP tool's cash-basis vocabulary.
