# Customer cash receipts: source contract (2026-09-24)

`analytics_get_customer_cash_receipts` answers the monthly cash-basis part of Timur's reports. It is a read-only, location-scoped finance aggregate. It does not use the `manual_cost` service value in `analytics_get_service_mix_trend`, and it does not produce payer cohorts.

## Backend trace

- Route: authenticated ERP `GET /finances_reports/annual_report/{location_id}/` (`PageFinancesReportsController::action_annual_report`). It requires `finances_year_report_access`; when the report-constructor feature hides system reports, the route redirects and the transport refuses it. The request-scoped user token is injected by `requestLegacyWebReport`, with no browser cookie or persisted session.
- Before that read, documented V1 `GET /user/permissions/{location_id}` verifies the effective annual-report right and account boundary for the same request identity. The backend finance filter treats an empty allowed-account list as no filter; for a user with `finances_accounts_limited_access=true`, this tool refuses an empty or malformed `finances_accounts_ids` list so that the report cannot inadvertently widen to all accounts. Missing permission metadata also fails closed.
- `getAnnualData` selects active (`st=YES`) finance transactions in authorized location accounts. It rounds the requested start down to the first day of its month and end up to the last day of its month. The tool therefore accepts only complete local calendar months, at most 12. The controller uses `dateAtTimezoneFilter` for the location; `CTableReportPeriod::fillData` assigns each transaction to its local month.
- `CTableReportPeriod` sums each signed transaction amount once by finance income category, using the stable `type` ID in a transaction drill-down link. It exposes a monthly income row and a period total. Account transfers without an income category do not enter the income rows. Canceled transactions are excluded by the source filter. A negative active transaction reduces the month/category net. The source does **not** split positive receipts from refunds or identify the corresponding original transaction.
- The category list includes standard categories and only active, location-linked custom categories (`ExpensesStorage::getBySalonIdsWithStandard`). A posted transaction in a subsequently disabled custom category can be omitted from this report. Reconciliation proves internal consistency of the rendered source, not completeness against every historical ledger row.
- Standard transaction type IDs come from `CTransactions`: service payment 5, product sale 7, miscellaneous income 8, client-account top-up 10, membership sale 6, certificate sale 12, and no-show penalty 13. The first four match the supplied PDF's core cash streams; memberships, certificates and penalties remain explicit rather than silently folded into miscellaneous income. All other income IDs are summed as unclassified posted income. An unclassified category may or may not represent customer cash, so `classified_customer_cash_net` excludes it; `posted_income_net` includes it.
- The parser checks one report table, expected month-column count, every row width, local month drill-down dates, unique positive category IDs, each row total, every monthly category sum against the income aggregate, and the period income total. A changed page or mismatch fails the whole call. The transport caps the HTML at 2 MiB. This is a complete source aggregate for the user's authorized accounts, not a transactional snapshot. The backend builds it from an unbounded transaction list; a busy clinic can time out or exceed the response cap, in which case the tool returns no partial total.

## Cash and privacy boundary

Client-account top-ups are a finance cash receipt; later spending of the deposit balance is a loyalty/deposit operation, not a second cash receipt in this report. `DepositBalanceChangeHandler` and `DepositsOperationsService` link top-ups to transaction type 10. `CTransactions` type 5 and type 7 are posted money transactions; loyalty deductions and historical service `manual_cost` are separate measures. The source's account permissions may hide accounts, so these totals are **authorized-account source totals**, not guaranteed whole-business ledger totals.

The report returns amounts and month keys only. It carries no names, phone numbers, email addresses, comments, or payment IDs. It reports signed **net** cash by stream. Gross receipts, refund totals, account-by-account reconciliation, a snapshot identifier, and custom income's customer meaning are unavailable.
The currency is emitted only when location metadata supplies an ISO 4217 code; otherwise it is `null`, never guessed from a symbol.

An authorized read-only smoke on demo location 4564 for August 2026 returned a nonzero, internally reconciled month. Its income total matched the existing P&L adapter on the same period. No client data or raw response was retained.

## Payer cohort investigation and decision

The finance web list `GET /finances/transactions_search/{location_id}/` is paged with an exact count and stable transaction IDs (`data-locator`), but `templates/finances/transactions/search.php` renders payer **names**, not client IDs. `GET /finance_transactions/{location_id}/{transaction_id}` returns a client ID, yet deriving a clinic-wide cohort would require a separate authenticated read for every transaction. The list also silently clamps the start date to `finances_last_days_count` in `FinanceTransactionsService::getDate`, without returning an effective period. Thus a complete, period-correct payer base cannot be proven by a bounded clinic-scale MCP call.

The existing `analytics_get_client_sales` source is not a substitute: `ReportProfit::getData(GROUP_BY_CLIENT)` composes goods transactions and attended service `cost` by visit period, not signed finance receipts or account top-ups. A client card's lifetime paid amount likewise has no selected-period cash basis. No payer deciles or stable payer targets are exposed until a server-side, permission-checked transaction aggregate provides exact period, stable client ID, money-source classification, refunds and pagination or snapshot completeness. Names are never matched to IDs.

The disabled Analytics Constructor report-data operations remain disabled. A future V3 finance read model can replace this temporary HTML adapter without changing the MCP tool's cash-basis vocabulary.
